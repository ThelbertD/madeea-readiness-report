Part one

MadeEA OS on a custom domain

The gateway you need is already built. The app around it is not ready to be published.

Orientation

Three things call themselves the app

Picking the wrong one is the most expensive mistake available here, so it is worth being exact before any DNS record is written.

The good news

The gateway is finished, not hypothetical

It is a full stack with per-user quotas, admin controls and a shared key pool nobody on the team ever sees. 61 gateway tests and 22 dashboard tests pass, all offline. It is blocked on infrastructure you are about to buy — and on nothing else.

How a request travels

4 hops · 1 public
Browser → gateway.yourdomain.com → verify JWT + quota → OmniRoute (127.0.0.1) → provider
  • OmniRoute never faces the internet — it binds loopback only. The authenticating proxy is the sole public process.
  • Streaming skips Vercel entirely — the browser calls the gateway directly, so a long reply cannot hit a serverless function timeout.
  • The master key lives in one file — the VPS .env at chmod 600. It is in no browser bundle.

What it already enforces

tested, not asserted

Each of these is covered by a test that runs with no credentials and no network — the suite boots a stub OmniRoute on loopback.

  • HS256 pinned on every JWT verify, which closes the alg: none confusion attack.
  • Admin role read from the database per request, never from the token — a demoted admin loses access immediately.
  • Quota rejects at the exact boundary, and a disallowed model is refused before any upstream call is billed.
  • An admin cannot lock themselves out, and the passcode hash is unreachable from any browser.
The honest part

A domain will not make all the AI work

This is the expectation worth resetting before spending anything. I counted what the 246 routes in source/ actually depend on.

So the domain delivers chat, model routing and the OmniRoute-backed views — the thing most people mean by "all the AI." It does not deliver Codex, Free Claude Code, OpenClaw, Hermes, the workspace and preview tabs, or anything vault-backed. Those were always going to stay on the machine that holds the files.

Before you deploy anything

Publishing source/ as it stands is a remote shell

Of 246 route handlers, 15 reference any authorization check. The other 231 are open to anyone who knows the URL. There is no middleware.ts — the Supabase login gate is client-side only, which stops a browser and stops nobody holding curl.

Several of those open routes spawn processes with caller-influenced arguments. Public, unauthenticated, and spawns processes is the definition of remote code execution on whatever machine runs it. Pointing a domain at source/ converts a private tool into that, in one DNS record.

The foundation is sound where it exists: supabaseServer.ts forwards the caller's own token rather than a service-role key, so RLS stays load-bearing and one missing check cannot expose everyone. That is the right design. It is simply not applied to 231 of the routes yet.

Sequence

The order to do this in

Each step proves the one below it is worth doing. Do not reorder them.

  1. Buy the domain and a small Linux VPSHetzner or DigitalOcean at the $5 tier is enough. Point an A record for gateway. at it and let DNS propagate before touching Caddy — the certificate is issued on boot and needs the name to resolve.
  2. Create the Supabase project and run the migrationTurn off public signup. The gateway creates users itself, because that is the only path that can check the team passcode.
  3. Bring up the stack and curl /healthA JSON ok:true over HTTPS is the whole proof that the hard part worked.
  4. Deploy the dashboard and set a real passcodeThe seeded hash matches nothing on purpose — nobody can register until an admin replaces it. Confirm chat streams end to end before going further.
  5. Then fix the shimPoint it at the new gateway and pass the signed-in user's token instead of the placeholder. Now the existing MadeEA OS export works from any browser.
  6. Rotate the keys before they travelomniroute-team-hub/.env already holds a generated master key and live Supabase secrets. It is correctly gitignored — but it sits inside OneDrive, which syncs it to a cloud account and every machine linked to it. Regenerate all of them, and keep the production copy on the VPS only.
  7. Only then consider exposing anything from source/And only behind a middleware that authenticates every route by default, with the CLI-spawning routes explicitly excluded rather than explicitly allowed.
Part two

The DM setter across social platforms

The setter can reach more platforms than you think — but not the two you probably want most.

Starting point

What runs today

Three workflows, one brain. Instagram is the only social channel; email already carries the late follow-ups because Instagram will not deliver them.

WorkflowChannelCadence

The good news

The plumbing is already multi-channel

This is the finding that changes the size of the job. The setter is not written against Instagram — it is written against GoHighLevel's conversation API, which is channel-neutral. Instagram appears in exactly two places.

Reading the inbox

one filter line

Qualify + Dedup walks the newest conversations and drops anything whose lastMessageType is not Instagram. Every other test in that loop — inbound only, not a teammate, old enough that they have stopped typing, not already handled — is channel-independent.

lastMessageType !== 'TYPE_INSTAGRAM' → continue

Sending the reply

one constant

Send Bubbles posts to /conversations/messages with type: 'IG'. That same endpoint carries Messenger, WhatsApp, SMS and email — the channel is the value of that one field, not a different integration.

POST /conversations/messages · type: 'IG'

So adding a channel that GoHighLevel already carries is not a rebuild. It is a filter value, a type constant, a tag namespace, and a decision about the delivery window — plus the part that actually takes judgement, which is tone.

Platform by platform

Where each one actually stands

Verdicts are about access, not effort. A platform with no messaging API cannot be reached by any amount of work that does not also risk the account.

PlatformRoute inVerdict
Facebook MessengerSame Meta Graph API family as Instagram, same 24-hour standard messaging window, already carried by GoHighLevel Filter + type constant. The window logic already written for Instagram transfers unchanged add first
WhatsApp BusinessCloud API. A 24-hour service window like Meta's; outside it only pre-approved template messages may be sent, and messaging is billed Carried by GoHighLevel, but templates must be submitted and approved in advance viable, with cost
SMSNative to GoHighLevel, no delivery window at all — the one channel that can carry the full ladder Trivially available. The constraint is consent law, not engineering viable, different rules
X / TwitterDM endpoints exist but sit behind a paid API tier with tight rate limits Not in GoHighLevel — needs its own integration and its own inbox handling conditional
LinkedInNo public API for personal messaging. Messaging access is partner-gated through the Sales Navigator and Recruiter programmes The tools that claim otherwise drive the browser or unofficial endpoints closed
TikTokNo public DM API. Business messaging is in-app and limited by region Nothing to integrate against closed

Platform terms move. Confirm the current window rules, tiers and rate cards at the moment you commit to a channel rather than trusting this table months from now — the verdicts are stable, the numbers behind them are not.

Worth flagging

LinkedIn is the one to say no to clearly

For a B2B setter, LinkedIn is usually the first channel anyone asks for and it is the one that cannot be done properly. There is no general messaging API. Access exists only inside partner programmes built for licensed Sales Navigator and Recruiter seats, and it is not open to general application.

Every off-the-shelf "LinkedIn automation" tool works around this by driving a logged-in browser session or calling endpoints never published for that use. That violates the User Agreement, and the enforcement lands on the sending account — restriction or permanent loss of the profile doing the outreach, which for a founder-led brand is the asset the whole channel depends on.

The defensible version is a person sending LinkedIn messages with the SOP open beside them. The setter can draft; it should not send. That distinction is worth writing into the plan now, because the tooling that blurs it is easy to buy and hard to unwind.

Do this first

The brain lives in three places, and channels multiply it

The SOP prompt is byte-identical across all three workflow files today, kept in sync by hand — the documentation's own instruction is "edit one and you must edit all three." That is already the sharpest edge in the system: a nudge written from a stale copy contradicts the conversation it is chasing, and nothing fails loudly when it happens.

Adding Messenger and WhatsApp takes three copies to five or seven. Extract the SOP and the guard set into one sub-workflow before adding any channel, not after. Retrofitting a single source of truth onto seven files that have quietly drifted apart is a materially worse job than doing it once at three.

The split is clean because most of the system is already channel-independent. The brain, the seven guards and the four silent exits are shared. What is genuinely per-channel is small: the inbound filter, the send type, the delivery window, the tag namespace, and the length rule — two bubbles suits a DM, and does not suit an email.

Sequence

The order that costs least

Deliberately front-loaded with the unglamorous step, because it is the one that gets skipped.

  1. Get Instagram fully live and read its draftsOne channel proven end to end teaches more about the SOP than two channels half-built. Every tone correction found here is a correction you do not have to make five times later.
  2. Extract the SOP and guards into one sub-workflowThe single highest-value change in this document. Do it at three copies, while they are still identical and the diff is empty.
  3. Add Facebook MessengerSame API family, same window, same GoHighLevel plumbing. It is the cheapest possible test of whether the extraction actually holds — and if it does not, you find out on the easy channel.
  4. Decide the consent posture, then add WhatsApp or SMSBoth are reachable today. Neither should ship before the cross-channel question above has an answer someone is willing to put their name to.
  5. Treat LinkedIn as a drafting surface, not a sending oneThe setter proposes, a person sends. This keeps the highest-value B2B channel open instead of risking the profile it runs on.
  6. Revisit X and TikTok only on a real signalBoth cost more than they return at current access levels. Revisit when inbound volume on those platforms justifies it, not on principle.
Unchanged by any of this

The setter still does not book anything

It sends the link. Nothing in any workflow watches a calendar, so "link sent" and "call booked" remain different facts on every channel you add. Adding platforms multiplies the first number and tells you nothing about the second — which makes the gap between them the measurement worth building before the next channel, not after.

Both tracks

The same defect, in two unrelated systems

Worth naming, because it is the one thing here that is cheap to fix now and expensive later.

In MadeEA OS, the browser shim exists in two copies — app/omni-shim.js and tools/omni-shim.js — and the second overwrites the first on every rebuild. In the setter, the SOP prompt exists in three copies across three workflow files, kept identical by hand.

Neither duplication fails loudly. Fix the shim in one place and the change survives until a rebuild quietly reverts it. Edit the SOP in one workflow and the other two keep running the old brain, contradicting the conversations they are chasing. In both cases the system reports success while doing the wrong thing, which is the most expensive category of bug to own.

Both are also at their cheapest right now. The shim copies are still in sync; the three SOP copies are still byte-identical. Every channel added and every deploy made from here widens the diff. Consolidate each to one source before scaling either track — it is a smaller task today than it will be at any future point.
